## 1. 现状诊断（已核对源码）

### 1.1 原版是什么

一个 2026 年七夕为妻子做的**私人纪念互动叙事网页**。13 个场景线性推进，无失败判定、无分支，本质是"互动绘本"而非游戏。技术上是纯 Canvas 2D + 原生 JS，单文件 `game.js` 约 2200 行，零依赖、零构建、无 `package.json`。

### 1.2 核对过的事实

### 1.3 六个必须先纠正的认知（读码得出，违背直觉）

**① 原版美术没有"水彩模拟"，只有模糊。**
全项目 20 余处 `ctx.filter = 'blur(...)'`（0.3px 角色内部 → 10px 光晕），配合 `wcShape` / `wcBlob` 的 `globalAlpha = alpha / layers` 双层半透明叠加。真正的颜料颗粒沉积、边缘加深、水痕**原版是缺失的**。
→ 这条决定了 2.5D 的视觉增量不是"复现水彩"，而是**补全水彩**——这是重制白送的最大价值。

**② 加载屏是假的。**
`game.js:2023` 写死 `setTimeout(hideLoading, 2700)`，进度条是 `style.css:134` 的纯 CSS 动画（`loadFill 2.5s forwards`）。加载页**不加载任何资源**。
→ "首屏 3 秒可交互"目前是个空头支票。引入 three.js 后必须改成真实进度驱动，否则基线一上线就破。

**③ 交互命中测试必须重写——这不属于"仅表现层"。**
原版所有 `onDown / onMove` 吃的是**屏幕 CSS 像素坐标**做圆形判定（如 `game.js:1104`、`1603` 的 `U.dist(x, y, catX, catY) < 40`）。分层进入 3D 后，指针必须先 raycast 到 z=0 的逻辑平面、再折算回设计坐标喂给原函数，否则 13 个场景的互动**集体失效**。
→ **准确表述是：设计不变，实现重写。** 这不推翻锚点，但必须把"微交互回归清单"列为硬验收项。

**④ 15 张 jpg 躺在部署根目录，等于白送 0.77 MB 首屏。**
且命名与场景不对应：`scene-02` / `03` / `04` / `06` 各有两张，缺 `09` / `12`。
→ 必须移出部署路径。同时它们正好是"少量资产"路线的现成来源。

**⑤ 字体依赖 Google Fonts CDN。**
`index.html:10-12` 引 `fonts.googleapis.com`。在微信大陆环境大概率不可达。
→ 高概率风险，需子集化内联 woff2。

**⑥ `script.js` 是 1673 行死代码。**
引用的 DOM 节点（`#loader` / `#confession-btn` / `#float-layer` 等）已不存在，且它会预加载那些 jpg。

### 3.2 可发现性：从 hint 文字到"引导光"

原版靠一行常驻 hint 文字。2.5D 下目标可能被前景遮挡（近景）或过小（后景）。改为四段递进，**全程禁用箭头**：

| 时间 | 手段 | 目的 |
|---|---|---|
| 进入 0–3s | 目标自发光呼吸脉动（emissive 正弦 ±15%，周期 1.8s） | 先让人自由观察，不打断沉浸 |
| 3–6s | 镜头自动 dolly-in 8%（一次，不回弹）+ 景深焦点收到目标上 | 光线引导比文字更早生效 |
| 6s | hint 毛笔文字淡入（沿用原文案） | 兜底，不抢戏 |
| 10s | 呼吸加强 + 一次极轻震（如可用） | 最后手段 |

**用场景内元素替代箭头**：S1 显示器屏幕自闪、S5 海浪出现一条发亮浪线、S11 窗户漏出一线暖光、S10 有光点主动飘向镜头。

**命中率保障**：交互目标单独一层，各挂屏幕空间 AABB（≥ 48px），拾取用"投影到屏幕空间再判定"，**不做 3D raycast 直接命中模型**。

```js
// 交互层元素定义
{ id: 'window', layerIdx: 2, aabbScreen: true, pad: 16, minSize: 48,
  glow: { type: 'emissive', amp: 0.15, period: 1.8 }, focusOnHint: true }
```

### 3.4 转场：别再黑场

原版"done → 等 2 秒 → 0.6 秒黑场"在 2.5D 下既太长、又浪费了"连续绘本"的机会。分三档：

| 档 | 保持时长 | 转场 |
|---|---|---|
| 普通推进（S1→S2 等） | 0.5s | **纸纹穿页**：镜头推入当前场景的纸纤维贴片，纸纹填满后直接在下一场景淡出，全程无纯黑 |
| 情绪落点（S7→S8、S9→S10） | 1.2–2.0s | 保持镜头抬升 / 拉远，再用 250ms 短黑承接情绪转折 |
| 首尾（S0 开、S12 收） | 2.0s | 纸纹 + 白光，呼应"合上绘本" |

实现：一个全屏 quad 贴水彩纸纹理，转场期间相机穿过该 quad，材质 alpha 走 0 → 1 → 0，用材质级 wipe 取代 `fillRect` 黑场。S0→S1 可做成"从信封口穿进去"。

### 3.5 反馈升级

- **震动**：微信 X5/XWeb 对 `navigator.vibrate` 支持不稳定，部分机型静默忽略；iOS Safari 完全不支持。**结论：震动只做加分项，绝不作为唯一反馈。** 调用必须落在真实手势栈内；否则一律视觉 + 音效兜底。只用两种震感：`10ms` 轻点反馈、`[8,40,8]` 情绪节点。
- **音频**：加载屏加"轻触开始"按钮，在手势内建 `AudioContext` 并 `resume()`，同时监听 `WeixinJSBridgeReady` 提前解锁 iOS 微信。这一步**同时解决自动播放限制与首屏可交互问题**。音效与音乐同调性，全部基于现有五声音阶 `[523,587,659,784,880]`；点击音用高八度短音，`done` 用三音上行动机。
- **粒子与镜头微动**：每场景 `done` 触发 < 8px / 0.25s 的相机震动；粒子池分前后两层（前景大颗粒慢速 / 后景小颗粒快速），靠 depth 区分复用。

### 3.6 2.5D 化最容易翻车的 5 个地方

| # | 翻车点 | 预防 |
|---|---|---|
| 1 | 视差让手指与目标错位，点不中 | 交互层不做透视变换；拾取走屏幕空间 AABB；B 类场景（S4 / S7 / S9）零视差 |
| 2 | 目标被前景遮挡或尺寸过小 | 碰撞体放大到 ≥ 48px 并加 `pad: 16`；必要时自动隐藏遮挡前景层 |
| 3 | 水彩半透明 + 景深把文案糊掉 | 底部文案 / 进度点走独立 UI 层，不参与任何后期与景深 |
| 4 | 全屏后处理过多，中低端安卓掉帧 | 全屏后处理只允许一项（景深或 bloom 二选一）；水彩走预渲染纹理而非逐帧全屏 shader |
| 5 | "穿页"转场期间穿帮 / 黑边 / 下一场景未就绪 | 转场前预加载下一场景全部贴片；穿页动画时长覆盖加载窗口；资源未就绪时退回短黑场 |

## 4. 技术架构（Three.js 技术负责人）

### 4.1 工程化选型

**结论：引入 Vite + TypeScript + ESM，但不引入任何 UI 框架、状态库或后处理库。**

| 维度 | 零构建（现状） | Vite + TS |
|---|---|---|
| three 体积 | importmap 全量约 1.2 MB min | tree-shake 后约 **150 KB gzip** |
| 2200 行单文件 / 13 场景 | 已到临界点，全局类名易冲突 | 模块边界 + 类型护栏 |
| shader | 无法组织（字符串拼接） | `.glsl` 独立文件 + 构建期编译校验 |
| 迁移成本 | — | 工具链 **1–2 天**；场景逻辑逐字搬运，不需重写 |
| 代价 | 无 HMR、无类型、体积失控 | 需要 npm，部署链路多一环 |

决策依据是硬约束反推：**three 的 1.2 MB → 150 KB 直接决定"手机首屏 3 秒"能否成立**，而 13 场景 × 4~5 层 + 自定义 shader 在无类型、无打包的条件下必然失控。详见 §7 裁决记录。

### 4.2 目录结构

```
7afternoon/
  index.html  style.css
  src/
    main.ts              # 唯一入口：装配 Engine
    core/                # Engine, Clock, StateMachine, SceneManager, EventBus
    render/              # Renderer, CameraRig, LayerStack, Compositor, Resources
    scenes/              # SceneBase.ts, registry.ts, S0..S12/
    shaders/             # watercolor.glsl, paper.glsl, dissolve.glsl
    input/               # PointerRouter(屏幕命中), HitPlane(Raycaster)
    audio/               # Music(Web Audio 合成迁移)
    ui/                  # loading, dots, text
    bake/                # 烘焙：复用 wcShape/drawBoy 等既有函数 → 纹理
  raw/                   # 15 张参考 jpg（.gitignore，不部署）
```

**依赖方向严格单向**：`main → core → { render, scenes, input, audio, ui }`；`scenes → render(只读接口) + shaders`；`render` 不反向依赖 `scenes`；`shaders` 是纯数据。**禁止场景直接 `new THREE.WebGLRenderer`。**

### 4.3 渲染与 2.5D 架构

- **双相机按场景声明切换**，不做两套管线。正交适合"平面绘本"（S0 星空、S1 办公室、S3 聊天类）；透视适合有纵深的自然场景（S5 海边、S7 雨天、S11 夜景楼群）。切换点藏在 fadeOut 黑屏内，用户无感。
- **视差**：正交下 `layer.position.x = -camX * parallax`；透视下相机真实移动天然产生视差，层只补 UV 偏移。另加指针驱动的 `camera.rotation` 微动（± 0.15 rad）。
- **层序**：`sky(0)` / `far(0.15)` / `mid(0.35)` / `ground(0.5)` / `actors(0.7)` / `fx(0.8)` / `fg(1.1)`。UI 走 DOM，**永不入 3D**。
- **载体**：每层一个 plane + alpha 贴图（2 个三角），**不建几何体**；仅信封、心等"出屏"元素用薄几何。

```ts
interface LayerCfg {
  id: 'sky' | 'far' | 'mid' | 'ground' | 'actors' | 'fx' | 'fg';
  z: number;
  parallax: number;
  kind: 'plate' | 'geo' | 'points';
  src?: string;                    // 烘焙纹理 key
  blend?: 'normal' | 'add';
  opacity?: number;
  scroll?: 'none' | 'x' | 'xy';
  depthFade?: [number, number];    // 分层预模糊的起止
}
```

### 4.4 场景系统迁移

原 `render(ctx)` 的语义**必须消亡**：原版每帧重画（`game.js:2181`），three 里改成"建一次、每帧只改 uniform / transform"。这是性能跃升的核心，也是迁移的主要工作量。

```ts
interface Scene {
  id: string;
  camera: 'ortho' | 'persp';
  layers: LayerCfg[];
  preload(onProgress?: (p: number) => void): Promise<void>;  // 真实进度来源
  enter(): void;
  exit(): void;
  update(dt: number, t: number): void;
  build(root: THREE.Object3D): void;       // 幂等，上下文丢失后可重放
  onDown(p: Vec3, hit: HitResult): void;   // p 已是逻辑平面坐标
  onMove(p: Vec3): void;
  onUp(p: Vec3): void;
  isDone(): boolean;                       // 取代 this.done 轮询
}
```

- **命中**：`input/HitPlane` 用 Raycaster 打各场景一张不可见的逻辑 plane，返回 `{ layerId, uv, world }`，热区判定仍在屏幕空间等距——**保证与原版手感一致**。
- **注册表驱动**：`registry.ts` 里 `defineScene({...})`，SceneManager 只认注册表 → 支持 `?scene=S6` 单场景调试、支持懒加载。

### 4.5 水彩质感的实现路径

| 路径 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A 离屏烘焙** | `OffscreenCanvas` 跑现有 `wcShape` / `drawPaper` → Texture | **像素级还原现有美术，零重画**；复用 100% 已有代码 | 显存 + 烘焙耗时；不可实时变 |
| B 自定义 shader | noise + domain warp + 边缘暗化 | 零纹理、可实时、缩放不糊 | X5 上 GLSL 风险高；逐像素 noise 是中低端 GPU 杀手 |
| C 后处理叠加 | 纸纹 + 边缘暗化 | 成本极低 | 只能叠加，不能独立成路 |

**推荐 A 为主 + C 为辅，B 仅用于动态元素。** 关键论证：锚点 3 说"程序化为主"——**A 的烘焙源就是现有程序化代码**，依然零外部依赖，只是把绘制从"每帧"搬到"首帧一次"。

| 坑 | 处置 |
|---|---|
| DPR | **上限 2.0，推荐 1.5**。4096² RGBA = 64 MB/张，骁龙 6 系共享内存两张即 OOM。DPR 与纹理尺寸解耦 |

### 4.9 风险最高的 3 个技术点

| # | 风险 | 最小验证实验 | 失败退路 |
|---|---|---|---|
| 1 | **X5 内 WebGL 稳定性与上下文丢失率**（决定方案是否成立） | 骁龙 6 系真机微信打开 200 行最小页：three + 2 层 plane + 1 个自定义 shader；前后台切换 20 次、切场景 50 次，统计丢失次数与恢复成功率，对照 Chrome / Safari | 丢失率 > 5% 或恢复白屏 → **混合渲染：three 只做背景视差，角色层用 2D Canvas 叠加**，保住 2.5D 观感 |
| 2 | **烘焙纹理的显存与耗时** | 把 S1 的 `render` 搬进 OffscreenCanvas 出 2048² 图，量单张耗时、单张显存、13 × 4 层全量内存 | 单张 > 20ms 或全量 > 96 MB → 降分辨率 / 降层数 / LRU 只驻留 2 场景 |
| 3 | **透视场景命中测试与原布局还原** | 用 S1（点击显示器）与 S7（纵深雨天）验证 Raycaster 打逻辑 plane 后，热区相对视觉的偏差 | 偏差 > 10% 视觉尺寸 → 视觉层与逻辑层分离，热区永远走屏幕空间等距判定 |

## 5. 视觉实现（技术美术）

### 5.1 水彩特征的拆解与落点

| # | 原版特征 | 代码依据 | 3D 复现手段 | 落点 |
|---|---|---|---|---|
| 1 | 多层半透明叠加 | `wcShape` / `wcBlob`，`globalAlpha = alpha / layers` | 3D 里不再叠，全部在 2D 烘焙阶段合成完毕 | 烘焙 |
| 2 | 软边 / 模糊扩散 | `ctx.filter = 'blur(0.3~10px)'`，20+ 处 | 烘焙 blur 打底 + shader 端 UV 噪声扰动做"毛边" | 双端 |
| 3 | 颜料颗粒 / 沉积 | **原版缺失** | `col *= mix(1.0, 0.86, fbm(uv * 9.0))` | shader |
| 4 | 纸张纤维 | `drawPaperTexture`：300 颗 1.5px @ α0.025 | 512² tileable noise，末端 multiply | 全屏 1 pass |
| 5 | 有机不规则轮廓 | `wcBlob` 用 sin/cos 调制半径 | 顶点低频噪声位移（≤ 2px 屏空间） | 顶点 |
| 6 | 局部饱和度不均 | `wcWash` 径向渐变 | 烘焙保留 + shader 大尺度 noise 调饱和 ± 8% | 双端 |
| 7 | **边缘加深 / 水痕** | **原版缺失** | 烘焙时对 alpha 做一次 box-blur 取差值，边缘叠 8% 同色深色 | 烘焙（强烈建议） |
| 8 | 大面积极浅渐变 | `drawSky` 三段线性渐变 | 保留；末尾加 1/255 dither 防 8-bit banding | shader |
| 9 | 软投影 | `drawShadow` blur(3px) α0.15 | 烘进角色贴图，**不要**用真阴影 | 烘焙 |

**架构铁律：所有半透明叠色只在 2D 离屏阶段完成。** 3D 里每层是一张"已合成的图"，层间只叠 2–3 层。原因见 §5.4——线性空间多次 alpha 混合会把暖色整体拉灰。

### 5.2 路线对比与选型

| 路线 | 成本（中端安卓 1080p） | 视觉收益 | 结论 |
|---|---|---|---|
| 噪声驱动边缘扩散 shader | +0.4~0.8ms/层 | ★★★★ 最像水彩的一环 | **上**，但只给角色层 + 前景层；远景层用烘焙 blur 代替 |
| 屏幕空间纸张纹理 | +0.15ms | ★★★★ 纸感命门 | **必上**，成本几乎为零 |
| 顶点 / 法线扰动 | +0.1ms（≤ 512 顶点） | ★★ 轮廓有机化 | 只给前景 1–2 层；细分 ≤ 16×16 |
| 后处理描边 | +1.2ms | ★ 原版角色无描边 | **砍** |
| 全屏边缘色散 / 色偏 | +0.9ms 且易脏 | ★ | **砍**（需要时降级为烘焙端 R/B 偏移 0.4px） |

### 5.3 分层扒图规范

**生成方式——ctx 代理 + 分帧烘焙，不破坏现有代码资产：**

```js
// 1) Scene 基类加 8 行，不改任何绘制函数
// 2) 给每个场景的 render() 插 3~4 行 tag()，标记层切换点
//    tag('far')  → drawSky / wcWash / drawStars
//    tag('mid')  → drawGround / drawTree / 房子 / 棕榈
//    tag('char') → drawBoy / drawGirl / drawCat
//    tag('near') → 前景剪影
// 3) ctx 代理把绘制转发到 activeLayer 的离屏 canvas
function layerCtx(raw) {
  return new Proxy(raw, { get(t, k) {
    const v = t[k];
    return typeof v === 'function'
      ? (...a) => v.apply(Active.layer.canvas2d, a)
      : v;
  }});
}
// 4) Game.render() 改 12 行
for (const L of scene.layers) {
  Active.layer = L;
  if (L.static && L.baked) continue;      // 静态层只烘一次
  scene.render(layerCtx(L.ctx));
  if (L.static) { L.tex.needsUpdate = true; L.baked = true; }
}
```

`drawBoy` / `drawGirl` / `drawCat` / `drawSky` / `wc*` / `drawPaperTexture` **零改动**；原版 `index.html` 仍可直接运行（作为灰度对照）。总改动约 **60 行**。

| 层 | 命名 | 内容 | 纹理尺寸 | 深度 z | 时机 |
|---|---|---|---|---|---|
| L0 远景 | `s07_far` | sky / wash / stars / clouds | 640 × 1024 | −6 | `enter()` 烘 1 次 |
| L1 中景 | `s07_mid` | ground / tree / house / palm | 768 × 1024 | −3 | 1 次 |
| L2 角色 | `s07_char_girl_happy` | 单角色 billboard | 384 × 384 | 0 | 按状态缓存 |
| L3 近景 | `s07_near` | 前景枝 / 栏杆 / 草（中心透明） | 1024 × 768 | +1.5 | 1 次 |
| L4 天气 / 光 | `s07_fx` | 雨 / 浪 / 光束 | 384 × 384 | +0.2 | **每帧** |

- **层数上限 5**（静态 4 + 动态 1）；中低端降到 3（L3 合进 L1，L4 降 256²）。
- **透明通道**：统一 32bit RGBA、**premultiplied**。
- **排序**：`renderOrder = 0..4`，全层 `depthWrite = false`、`transparent = true`，靠手写 renderOrder 排序，**不要**依赖 three 的自动透明度排序。
- **分辨率原则**：按"设计宽 750"而非屏幕物理像素。1080p / DPR3 的手机上纹理被放大约 1.4×——水彩软边天生吃上采样，这是本项目最大的性能红利。
- **指针映射**：Raycaster 与 z=0 的不可见 Plane 求交 → 世界坐标 → 除平面宽 × 750 → 喂 `scene.onDown / onMove / onUp`。

### 5.4 色彩管理（最关键，最容易毁掉整个项目）

| 项 | 配置 | 原因 |
|---|---|---|
| `renderer.outputColorSpace` | `THREE.SRGBColorSpace` | 唯一正确出口 |
| 颜色贴图 `colorSpace` | **必设** `THREE.SRGBColorSpace` | canvas 烘焙已是 sRGB；**漏设 = 画面整体提亮、发白、对比度塌陷**（M1 实测 `#FF8B7B→#FFC3B8`、`#2A2050→#716398`，最大偏差 **72/255**）。本项目第一大坑 |
| 纸纹 / 噪声 / mask | `THREE.NoColorSpace` | 它们不是颜色，不做 sRGB 解码 |
| `toneMapping` | **`THREE.NoToneMapping`** | ACESFilmic 会把 `#FF8B7B` / `#FFC857` 去饱和 + 压暗 → 脏、灰，正好毁掉暖色水彩 |
| 手动 gamma | **不需要** | 双端都在 sRGB，再 pow 一次就废 |
| alpha | 统一 **premultiplied**：`mat.premultipliedAlpha = true` + `NormalBlending` | 非预乘会在软边留白 / 黑 halo |
| 线性空间叠层 | **禁止** | 多层 alpha 在线性空间混 → 整体偏灰 |
| 背景 | `scene.background = new THREE.Color('#FBF6EE')` | 原版纸底，禁纯黑 |
| AA | `antialias: false` | 水彩软边对 AA 不敏感，省带宽 |

**自检方法（已实现并跑通 → `scripts/check-color.mjs`）**：铺原版调色板色卡 → `gl.readPixels` 逐格回读 → 与真值比对。刻意做成**三路对照实验**：

| 路径 | 做法 | 期望 |
|---|---|---|
| `unlit` | `MeshBasicMaterial({color})` | 全通过 |
| `tex-srgb` | 贴图 `colorSpace = SRGBColorSpace` | 全通过 |
| `tex-linear` | 贴图**故意不设** colorSpace | **全失败**（错误对照组） |

`tex-linear` 若"通过"，说明自检自身失效，**结论一律不可信**。有了对照组，才能区分"链路对了"和"检查器坏了"。

> 📌 **M1 实测记录（2026-09-12）**：`unlit` 8/8 Δ0 ｜ `tex-srgb` 8/8 **Δ0**（像素级零误差往返）｜ `tex-linear` 0/8 Δmax **72**。
> 并**修正了本节原始结论的方向性错误**：漏设贴图 colorSpace 的症状是**变亮发白**，不是"变暗发灰"。
> 机理是 sRGB 字节被当作线性值读入、输出端又编码回 sRGB，中间调被整体抬升。方向搞反，调参会越调越远。

### 5.5 后处理链取舍

| 效果 | 用不用 | 参数方向 | 成本 |
|---|---|---|---|
| 纸张纹理 | **必上** | 512² tileable，`col = mix(col, col * paper, 0.05)` | ~0.15ms |
| 暗角 Vignette | **上** | radial 0 → 0.18（S7 用到 0.32） | ~0.10ms |
| 颗粒 Grain | **上，但用纸纹代替** | 静态 3 帧循环（**禁随机噪点**：会闪且不像水彩），强度 3–6% | 0 |
| Dither | **必上** | Bayer 4×4，± 1/255 | ~0.05ms |
| Bloom | **仅 S0 / S11 / S12** | threshold 0.85 / strength 0.3 / **1/4 分辨率** / 2 次高斯 | ~0.8ms |
| 景深 DoF | **真 DoF 砍** | 改"分层预模糊"：far blur 2–3px、near blur 4–6px、角色 0px | **0** |
| 色差 CA | **砍** | 需要时降级为烘焙端 R/B 偏移 0.4px | — |
| 全屏描边 | **砍** | 原版无描边 | — |

**最终链**：`各层 → 合并(1×) → 纸纹(×) → 暗角(×) → [bloom(add) 仅夜景] → dither`。全屏 pass ≤ 2（夜景 3）。
用分层预模糊冒充景深是这风格下的完美近似——水彩本来就"哪层都可以软"。

### 5.6 移动端材质预算

| 项 | 目标值 |
|---|---|
| 渲染分辨率 | `min(devicePixelRatio, 2) × 0.9`（原版 `game.js:2036` 取 DPR **无上限**，DPR3 白烧 2.25× 填充率，必须 clamp） |
| 单层贴图 | 远 / 中 / 近 ≤ 1024²；角色 ≤ 384²（推荐 256）；FX ≤ 384² |
| 总 VRAM | ≤ 40 MB（mipmap 展开后 RGBA8） |
| Mipmap | 开；`LinearMipmapLinearFilter`；`anisotropy = 2` |
| 压缩 | **不用 KTX2 / Basis**：块压缩在"平滑渐变 + 软边"上出块状伪影，恰是水彩最怕的。策略为运行时烘焙（0 下载）为主，必要时 WebP q0.88 |
| Draw call | ≤ 6/帧 |
| 材质 | 共享 2 个 material（static / dynamic），避免 shader 变体膨胀 |
| 几何 | `PlaneGeometry(1,1,16,16)` 复用，总顶点 < 3k；**不用 Sprite**（无法合批） |
| 每帧上传 | 仅 FX 层（≤ 384² ≈ 0.6 MB，1 次 `texSubImage`） |
| 三档降级 | 高：全链 + 5 层 → 中：关 bloom、分辨率 ×0.8 → 低：砍 near 层、FX 降 256²、纸纹并入合并 pass |

### 5.7 角色方案

| 方案 | 换表情 | 呼吸 / 微动 | 工作量 | 质量上限 | 结论 |
|---|---|---|---|---|---|
| A. 现有函数 → 离屏 billboard | 重烘 1 张 256²，缓存 key = `who + expr + blink + blush` | 顶点正弦 + `scale.y 1.008` | 低 | 中（= 原版） | **推荐主力** |
| B. 高精度静态立绘 | 需重画 | 同上 | 中高 | 高 | 仅 S0 / S12 用（海报级） |
| C. 骨骼化 2D 纸片人 | 支持 | 最好 | 最高 | 高 | 不做，超范围 |

**A + 拆分微动效**：

- **呼吸**：`scale.y = 1 + sin(t * 2.6) * 0.008`，`position.y += sin(t * 2.6) * 0.015`
- **眨眼**：眼睛单独一张 64² plane（z = +0.01），每 3–5s 随机播 2 帧、120ms 闭合。比整体重烘便宜 10×
- **站立摆动**：`rotation.z = sin(t * 1.7 + phase) * 0.012`（约 0.7°），两人相位错开 0.9
- **换表情**：嘴 + 眉单独一张 96 × 64 plane，4 种 expression 预烘，主体躯干永不变。只有换装才整张重烘
- **猫 purr**：原版 `drawCat(ctx, x, y + sin(petT * 10) * 2, …)`（`game.js:1584`）→ 映射到 `plane.position.y += sin(t * 10) * 0.02`，1:1 还原

### 5.8 光照与情绪

| 场景 | ambient 色 / 强度 | hemi(天/地) | dir 色/强度 | Fog | tint | 饱和 | 光晕 |
|---|---|---|---|---|---|---|---|

## 6. 实施路线图（制作人）

### 6.1 试点场景：选 S3，不选 S0 / S12

理由：**S3 除夕夜聊天是全片最"平"的一场**（两人 + 窗 + 手机光），也是文本最密的一场。海边（S5）、星空（S0 / S12）天然有纵深，不验证也成立；**只有让最平的场景立起来，13 场才全部有解**。它同时压测三个真风险：夜景光照与水彩 shader、WebGL 上叠加中文小字的可读性、"心动"这一情绪点能否被运镜放大。

**原版保留程度：100% 冻结，不做任何原地重构。** v2 独立开发在 `/v2/`，`main` 根目录在 M4 验收前不动一个字节；通过后原版移入 `/classic/` 长期保留。

### 6.3 关键路径

瓶颈有两个，性质完全不同：

**A. 否决性瓶颈（可提前一周消除）——微信 X5/XWeb 在低端安卓的真实 WebGL 表现。**
这不是优化题，是"锚点 1 是否成立"的生死门。X5 有大量已知的 WebGL 降级与软件渲染（SwiftShader）案例。拆解：M1 用 2 周、一台低端真机、一个场景，一次性给出 yes/no，**绝不推迟到 M3 才发现**。

**B. 长尾关键路径（真正的工期黑洞）——单作者 × 13 场景 × 分层贴片的美术产能。**
一个人只能串行，且作者不是美术。拆解：把成本从 `O(13 × N)` 降到 `O(13 + N)`——先建"通用图层套件"（天空 / 地面 / 植被 / 光斑 / 纸纹 / 雨雪）+ 场景模板，每场只画 2–3 个独特前景层。M2 的"60% 复用率"就是为这条路径设的闸门。

## 7. 裁决记录（角色冲突与主创判定）

### 裁决 1：Vite + TS **胜出**，但采纳制作人的告警

- 技术负责人主张 Vite + TypeScript（tree-shake 1.2MB → 150KB、类型护栏、`.glsl` 独立文件）。
- 制作人主张 vendored ESM + importmap，保住"零依赖零构建"与 Pages 直推。
- **判定：采用 Vite + TS。** three 的体积差直接决定"手机首屏 3 秒"能否成立，这是硬约束；13 场景 + 自定义 shader 在无类型无打包下必然失控。
- **但采纳制作人的三条约束**：① "本地能跑、Pages 白屏"列为 M1 显式验收项；② 构建产物直接进 Pages，不引入复杂 CI；③ 退路是 importmap + vendored ESM——因为运行时本来就是 ESM，退回无损。

### 裁决 2：澄清"只重制表现层"的真实含义

用户选择的锚点 2 是"只重制表现层"。但三位技术与美术角色**各自独立**指出同一件事：**交互的实现必须重写**，因为原版是屏幕像素坐标的圆形判定，分层进 3D 后必须走 raycast → 逻辑平面 → 设计坐标折算。

- **锚点没有被推翻**：剧情、交互设计、情感走向 100% 不变。
- **但准确表述是：设计不变，实现重写。**
- **后果**：必须把"微交互回归清单"（13 场景 × 命中区域 / 阈值 / 完成条件）列为 M3 的硬验收项，否则会出现"看起来一样但点不中"的隐性退化。

### 裁决 3：S3 作为首个试点（策划与制作人一致）

技术侧倾向用有纵深的场景（海边 / 星空）验证，因为"效果好看"。制作人反对：**天然有纵深的场景不验证也成立，只有最平的场景立起来，13 场才全部有解**。判定采制作人。

### 裁决 4：三条独立发现交叉印证，升格为方案前置项

| 发现 | 提出者 | 处置 |
|---|---|---|
| 加载屏是假进度（硬编码 2700ms + CSS 动画） | 技术负责人 / TA / 制作人 **三方独立命中** | 升格为方案前置项，见 §4.7 |
| 15 张 jpg 躺在部署根目录白送 0.77MB | 技术负责人 / 制作人 | 移出部署路径；同时作为"少量资产"来源 |

## 9. 制作人的最后一句提醒

**这个项目最可能失败的真实原因，不是需求变更，也不是技术难度——而是它会被"技术指标的成就感"劫持。**

唯一有裁决权的用户只有一个人，且只会认真看一次；但工程决策每天都在产生可量化的正反馈——帧率涨了、shader 更漂亮了。当两者冲突时，单作者几乎必然选择可量化的那一侧，最后交付一个技术漂亮、却没有任何一个瞬间击中人心的东西。

第二条真实原因：13 场全量迁移的边际成本被低估。一个人串行做美术，会在第 6–8 场时热情耗尽，而此时既不能发布也不能放弃。

第三条：为只有一次机会的体验承担了全部技术风险——首因被一次白屏或一次掉帧消耗掉，就没有第二次。

**所以：发布即胜利。M4 之后冻结 v1.0，不要再改。**

## 10. M1 施工记录：三个把画面搞挂的坑（2026-09-12）

S3 的 2.5D 装配跑通了，但过程中撞上三个**互相叠加、表象相似**的坑，
每一个单独拿出来都足以让画面全黑。记下来，因为第 1 个的迷惑性是教科书级的。

### 坑 1：三个 drawcall 数据全对，画面只剩清屏色（背面剔除）

**现象**：`renderer.info` 报 `calls: 8 / triangles: 16`，5 张贴图全部上传，
相机投影矩阵逐元素正确，命中链路归一化误差 2.78e-17 —— 但 `toDataURL()`
拿回来的是 750×1624 纯 `#FBF6EE`（清屏色）。逐层显隐做消融实验，差值纹丝不动。

**根因**：为了拿到原生"y 轴向下"的设计坐标（命中链路依赖它），正交相机写成
`OrthographicCamera(-0.5, 0.5, -0.5, 0.5, ...)` —— **top/bottom 取了负值**。
投影矩阵 y 缩放因此是 `-2`，**行列式为负 ⇒ 三角形绕序被整体翻转** ⇒
three 对 `FrontSide` 材质默认开启的背面剔除（`frontFace: CCW` / 剔除 `BACK`）
把每一个正对相机的贴片都剔掉了。

**修法**：`side: THREE.DoubleSide`。贴片全是正对相机的平面，不增加任何绘制成本，
却保住了那条已验证的坐标换算链。**不要**为了这个去改相机。

**诊断序列**（那次是靠这个序列破的案，值得记）：

| 步 | 动作 | 观察 | 排除掉什么 |
|---|---|---|---|
| 1 | 改清屏色 → 读回 | 读回跟着变（品红/纯黑） | 读回路径、帧缓冲、`preserveDrawingBuffer` 都正常 |
| 2 | 塞一个裸红平面（无贴图/不透明） | 仍不出 → 不是贴图/材质问题 | 烘焙资产 |
| 3 | raw GL 直接 `drawArrays` 全屏三角形 | 出得来（返回蓝色） | GL 上下文、viewport、着色器编译 |
| 4 | 查 `cullFace` / `frontFace` / `cullFaceMode` | `true` / `CCW` / `BACK` | **破案** |

### 坑 2：位置全对、内容上下颠倒（贴图 flipY）

**现象**：男孩是倒着的，但四个气泡的位置完全正确。

**根因**：坑 1 那台 y 轴向下的相机把整幅画面上下翻转了，而 three 默认
`flipY = true`（把图片首行放到 UV 的 `v=1`），两者叠加正好翻反。
**层位置不受影响**（网格中心 0.5 是对称的，映射后位置恰好不变），
所以表现为"位置对、内容反"——这个组合本身就是该坑的指纹。

**迷惑点**：全屏渐变翻转后仍然"像那么回事"（navy→purple 都是暗紫），
只有画到具体角色才露馅。实测把 `sky` 的 `flipY` 一翻，保真差 **9.35 → 2.26**，
才确认是全局方向问题而非某层错位。

**修法**：`loader.ts` 里 `tex.flipY = false`，与 y 向下的相机配套。

### 坑 3：`page.screenshot()` 抓不到 WebGL 内容

**根因**：默认 `preserveDrawingBuffer: false`，缓冲在合成后即被丢弃。

**修法**：`Stage` 接受 `preserveDrawingBuffer` 选项，由 `?capture=1` 打开；
生产路径绝不开（有每帧缓冲拷贝的代价）。读回必须在 `render()` 之后的**同一帧内**
`canvas.toDataURL()`。

**⚠️ 这个坑最容易误诊**：它的表象是"画面平均差 177/255"，
和"渲染全挂"长得一模一样。而当时坑 1 真的同时存在，
两个 bug 叠在一起互相掩护，白烧了一轮排查。

→ 因此冒烟测试加了一条**前置自证**断言：`帧读回非空白`（检查亮度 std）。
读回一旦是纯色就先报这一条，不让人误以为是渲染问题。

### 附加发现：`MultiplyBlending` 的语义其实是对的

一度怀疑纸纹层的乘法混合会把透明区乘成黑色（`Cb × Cs × αs`，α=0.025 时系数仅
0.0136）。查 three 源码确认预乘路径是：

```js
gl.blendFuncSeparate(gl.DST_COLOR, gl.ONE_MINUS_SRC_ALPHA, gl.ZERO, gl.ONE)
// = Cs·αs·Cb + Cb·(1-αs) = Cb · (1 - αs(1-Cs))  ← 与 Canvas2D multiply 完全等价
```

但要证明"纸纹真的生效"不能靠分块均值：300 个 1.5×1.5 的点只占 0.11% 像素、
每点暗化 1.1%，落到块均值上是 1e-4 量级。**必须单开一个逐像素探针**，
否则"某一层其实没生效"会一路蒙混过关。探针同时能识别混合语义写错
（若真的乘成 `Cb×Cs×αs`，单点 Δ 会飙到 ~250 而不是个位数）。
